## 一、撮合引擎架构

### Q1. 撮合引擎为什么必须主备双活？单点不行吗？fencing token 如何防脑裂？

**解析：** 撮合是全站核心路径，单点故障=全站停摆=用户恐慌+资损。但纯主备切换有脑裂风险（网络分区导致双主同时撮合→重复成交、双写资金）。fencing 的核心：备升主时携带一个单调递增的 fencing token（epoch/lease generation），所有下游服务（资金、行情、Kafka 写）只接受最新 token 的写请求。旧主恢复后发现自己 token 落后，写被下游拒绝→自动降级为备。**关键陷阱**：不能只靠心跳判活，心跳静默=脑裂根因，必须 fencing + lease 双保险。lease 主周期续约，过期备升主；续约窗口要 < 故障检测窗口，> 网络抖动。

### Q2. 内存撮合 + 快照 + offset 回放：宕机后怎么恢复？为什么不直接用 WAL 全量回放？

**解析：** 内存撮合快但易失，宕机后需重建订单簿。方案：周期快照（每 N 秒/N 笔）订单簿全量 + 记录当前 Kafka 消费 offset；恢复=加载最近快照 + 从该 offset 重放 Kafka 到最新。不直接全量 WAL 回放是因为每笔落盘延迟高，且恢复时长交易所有成千上万笔委托要全量回放慢。快照+回放是"定期全量+增量"折中。**陷阱**：快照必须和 offset 原子对应（快照时记录当前消费 offset），否则回放起点错会漏单或重复；快照过程要 stop-the-world 或 copy-on-write 避免状态移动。对比 LMAX 用 event sourcing 全量回放（无快照），恢复慢但实现简单，适合量级小的场景。

### Q3. 为什么撮合"单 symbol 单线程"？多 symbol 能不能共享一个线程？

**解析：** 同一交易对的订单有先后依赖（先来的先撮），必须串行化；单线程无锁=最快路径，避免锁竞争。多 symbol 互相独立，可多线程/多进程（每 symbol 一个 goroutine/线程）。**陷阱**：跨 symbol 套利/IOC 跨市价单需要跨线程协调，罕见但要特殊设计。规模上，单 symbol QPS 极高时单线程会打满 CPU，可上 CPU pinning 绑核 + busy-loop 减少调度。批量撮合（时间轮每 X ms 撮一批）降低单笔调度开销、提高吞吐，代价是牺牲微秒级延迟——现货加密 ms 级延迟容忍，可接受。

### Q4. 批量撮合（batch matching）和逐笔撮合的取舍？什么场景用哪个？

**解析：** 逐笔每笔立即撮合，延迟最低（μs），但每笔 CPU 调度开销大，QPS 高时打满。批量时间轮每 N ms 撮一批，吞吐高但延迟=N ms。现货加密（ms 延迟容忍）→批量；传统 HFT（μs）→逐笔+CPU pinning。**陷阱**：批量内同价位订单必须按时间戳排序，不能因批量打乱顺序（否则公平性问题和操纵嫌疑）。批量大小 N 要权衡：N 大吞吐高但延迟增；N 小延迟低但调度开销占比高。一般现货 N=1-10ms。

### Q5. 主备撮合"主"宕机，备升主时如何保证不丢不重？

**解析：** 不丢：备通过消费同一个 Kafka（委托流）跟随，备的 offset ≤ 主的 offset；升主后从备 offset 继续消费。不重：成交事件写 Kafka 带 TradeID 幂等，下游消费重复成交靠 TradeID 去重。**关键**：备的订单簿状态必须和主一致，靠"同样的输入流 + 确定性撮合"——撮合必须是纯函数（相同输入→相同输出），不能有随机数/墙钟时间戳/NTP 抖动依赖导致主备发散。**陷阱**：主写成交到 Kafka 和备消费 offset 要有顺序保证；fencing 防止旧主恢复后继续写成交（旧主 token 落后被拒）。

### Q6. lease 续约窗口和故障检测窗口怎么定？太大太小各有什么问题？

**解析：** lease TTL = 主续约周期 × N（如 3×），续约间隔 < TTL/3。太大：主真宕机时备等太久才升主，停摆时间长（可用性差）。太小：网络抖动→主来不及续约→备误升主→脑裂（一致性差）。折中：加密交易所 TTL 几秒级可接受（ms 级停摆容忍）；传统 HFT 要亚秒级。**陷阱**：fencing 是兜底——即使误升主，token 保证只有一方能写下游，避免真正双写。还要配多数派协调（etcd/zk quorum）不只靠单点心跳，降低误判。

### Q7. 撮合引擎为什么不用数据库做持久化，而要内存+快照+Kafka？

**解析：** DB 每笔落盘=磁盘 IO + 事务开销=ms 级，撮合要 μs/ms 级，DB 扛不住高频撮合。内存撮合=零 IO 延迟，快照+Kafka 提供持久化和恢复能力。Kafka 顺序写磁盘+页缓存=吞吐高，异步落盘够快。**陷阱**：成交结果最终要落 MySQL（业务凭证+清算对账），但那是异步消费，不在撮合关键路径上。撮合关键路径只动内存+Kafka 写（顺序写快），DB 写在旁路。

### Q8. 撮合引擎部署单实例还是多实例？如何横向扩展？热点 symbol 怎么办？

**解析：** 单 symbol 单实例（绑核），多 symbol 多实例（每 symbol 或 symbol 组一个实例）。横向扩展按 symbol 分片，不同 symbol 路由到不同撮合实例（类似 Kafka 分区，HashPartitioner 按 symbol）。热点 symbol（BTC/USDT）单实例打满→一般不拆价格档位（跨档位有依赖），靠 CPU pinning + batch + 升级语言（Go→C++/Rust）解决。**陷阱**：跨 symbol 套利订单需多实例协调，少见但要设计好（如套利订单拆成多个 sub-order 分别路由）。symbol 到实例的映射要稳定（不轻易迁移，否则状态迁移成本高）。

## 二、撮合算法

### Q9. 限价单的价格优先 + 时间优先为什么这么定？能不能只看价格？

**解析：** 价格优先：买价高者优先成交（出价高=更想买），卖价低者优先。时间优先：同价位先到先成交（公平）。只看价格不行：同价位不分先后=不公平+操纵（插队）。**陷阱**：时间优先要求精确的全序时间戳；分布式下用单调递增 seq，不能用墙钟（NTP 抖动会导致乱序，破坏公平性）。撮合引擎内单线程发号保证全序。另外，"时间"是接收时间不是用户本地时间（防篡改）。

### Q10. 市价单吃深度时如何处理？IOC/FOK/POST-ONLY 区别和适用场景？

**解析：** 市价单按对手盘深度逐档成交，直到吃完或额度用完。IOC（Immediate or Cancel）：能成交多少成交多少，剩余立即撤——适合"想立即成交但不想留挂单"。FOK（Fill or Kill）：要么全部成交要么全部撤——防部分成交留下敞口（套利单常用）。POST-ONLY：只做 maker，若会立刻 taker 成交则拒绝——保证挂单拿 maker rebate（做市商常用）。**陷阱**：市价单吃深度可能滑点巨大（薄盘），必须配价格保护（偏离阈值拒绝），否则用户可能 5% 价格成交（胖手指）。

### Q11. 撮合价位数据结构用红黑树还是哈希表+链表？为什么 LMAX 用数组？

**解析：** 红黑树按价格排序，O(logN) 插入/查找最优价，适合价位多。哈希表（价位→链表）+ 最优价指针：O(1) 查最优，链表存同价位 FIFO 订单，但要维护最优价指针更新（删除最优价后找次优）。LMAX 用数组（按价位索引）：价位离散有限时 O(1) 最快，但价格粒度受 tick 限制且要预分配。加密交易所 tick 粒度细、价位范围大→红黑树或跳表；高频固定 tick 场景→数组。**陷阱**：维护"买一卖一"指针的原子性，删除最优价订单后要能 O(1) 找到次优（指针不能悬空）。

### Q12. 为什么撮合要区分 maker 和 taker？费率怎么设计？

**解析：** maker 挂单被别人成交（提供流动性），费率低甚至返佣。taker 主动吃单（消耗流动性），费率高。目的：鼓励挂单=增加深度=市场更健康（深度好→滑点小→用户多）。POST-ONLY 订单就是为 maker 设计（避免误成 taker）。**陷阱**：成交时 maker 是被动方，要靠订单"先存在于订单簿"判定，不能靠成交时戳判定（成交时戳两者相同）。maker/taker 费率差异要写入订单成交记录，清算时按角色分账。

### Q13. 止盈止损单在撮合引擎里怎么实现？为什么不能放前端？

**解析：** 止损单监控行情，触发价达到后转市价/限价单提交。需引擎持续订阅行情监控价格。不能放前端：前端关闭=失效；多端不一致；可被前端篡改触发（用户改前端绕过止损=风险）。实现：引擎订阅行情，条件满足→生成委托进撮合。**陷阱**：止损市价单在闪崩时滑点巨大（5·19 爆仓案例），要价格保护+熔断+可能转限价止损（止损限价单）。触发逻辑要用标记价（合约）或最新价，且要防"插针"误触发（用一段时间内突破才算触发）。

## 三、订单系统

### Q14. 订单状态机为什么需要 version 乐观锁？悲观锁不行吗？

**解析：** 高并发下单/撤单，同一订单可能被多个请求并发改状态（成交更新 + 撤单同时来）。version 乐观锁：`UPDATE ... WHERE id=? AND version=?`，失败重试，无锁等待，吞吐高。悲观锁 `SELECT...FOR UPDATE`：阻塞、死锁风险，撮合高频路径扛不住。**陷阱**：重试次数限制（避免活锁）+ 状态校验（撤单时若已 FILLED 不能撤，返回失败而非重试）。version 必须在状态机每次迁移自增。资金冻结也用乐观锁，但热点账户单独处理（子账户分片）。

### Q15. TradeID 幂等：为什么成交不能靠订单ID去重？

**解析：** 一个订单可能多次部分成交，每次成交一个 TradeID；订单ID是"一委托"，成交ID是"一成交"，语义不同。重复消费 Kafka 成交事件时，靠 TradeID 去重（INSERT IGNORE / 唯一索引），避免重复扣款。订单ID去重会丢失"多次成交"语义（把多次部分成交当一次）。**陷阱**：TradeID 要全局唯一（雪花/UUID/撮合引擎发号），不能依赖 MySQL 自增（多撮合引擎并发会冲突）。TradeID 作为幂等键要稳定且贯穿全链路（撮合→清算→推送→对账）。

### Q16. outbox 模式解决什么问题？为什么不能"先写DB再发Kafka"或"先发Kafka再写DB"？

**解析：** 问题：写 DB 和发 Kafka 是两个动作，不能原子。先写 DB 后发 Kafka 失败=消息丢（下游永远收不到）；先发后写=消息有但 DB 没记录=数据不一致（用户看到成交但订单状态没变）。outbox：业务表 + outbox 表在同一个 DB 事务写；后台轮询 outbox 发 Kafka，发成功标记/删 outbox 行。效果：DB 事务保证不丢，Kafka 至少一次发送（可能重复→靠消费端幂等兜底）。**陷阱**：outbox 轮询有延迟（秒级），可上 Debezium 监 binlog 实时发 Kafka（CDC 方案）；消费端必须幂等（TradeID 去重）。

### Q17. 撤单请求和成交竞态怎么处理？撤单成功后又来了成交怎么办？

**解析：** 场景：用户点撤单瞬间，订单正好被撮合成交，两个请求并发。处理：状态机 + version。撤单尝试把订单从 NEW→CANCELED，若此时已 PARTIALLY_FILLED/FILLED，撤单失败（version 不匹配或状态校验拒绝）。已撤单的订单在撮合引擎内存订单簿里已被移除，不会再成交——竞态实际发生在"API 层读订单状态 vs 撮合写订单状态"。**陷阱**：返回给用户的撤单结果要准确（撤单时可能正好成交，需回查最新状态再返回，不能返回"撤单成功"但实际已成交）。

### Q18. 订单状态有哪些？为什么需要这么多中间状态？

**解析：** NEW（已接受）→PARTIALLY_FILLED（部分成交）→FILLED（全部成交）/CANCELED（撤销）/REJECTED（拒绝）。中间态 PARTIALLY_FILLED 必要：多次部分成交要记录已成交量，方便用户实时看 + 对账 + 撮合引擎内存订单簿维护剩余量。**陷阱**：REJECTED（风控/余额不足拒绝）和 CANCELED（用户主动撤）要区分，影响统计（拒单率 vs 撤单率）和资金退还路径（虽然都解冻，但原因不同）。状态迁移必须单向 + version，不能回退（FILLED 不能回 PARTIALLY_FILLED）。

### Q19. 委托记录写 MySQL 和撮合引擎内存订单簿如何保持一致？

**解析：** 委托先进 MySQL（凭证）+ outbox，再经 Kafka 进撮合引擎内存订单簿。一致性：outbox + Kafka 保证撮合引擎一定收到委托（at-least-once）；撮合幂等保证重复不乱（同委托重复消费不重复挂单，靠委托 ID 去重）。撮合引擎内存订单簿是"热副本"，MySQL 是"冷凭证"；成交后消费成交流更新 MySQL 订单状态。**陷阱**：撮合引擎宕机恢复时，内存订单簿从快照 + Kafka 重建，必须和 MySQL 委托一致——靠"相同输入流 + 确定性撮合"保证，所以撮合必须是纯函数。

### Q20. 订单的成交顺序为什么必须全局有序？seq 怎么设计？

**解析：** 同一订单的部分成交顺序影响用户看到的状态演变和资金变化顺序，必须有序。seq 设计：per symbol / per user 两层；raw_seq（撮合发号）+ push_seq（前端推送）。不能用 Kafka offset：多 symbol 共享一个分区时 offset 对某 symbol 不连续（夹着别的 symbol），且聚合后（100ms 聚合成一条）offset 和推送消息非 1:1。实现：固定 symbol 实例本地原子计数器（零 Redis 开销），周期快照到 Redis 供故障切换续号。**陷阱**：推送层重连增量回放靠 seq，gap 时回退全量快照重建，所以 seq 必须连续单调可校验。

## 四、资金系统

### Q21. 资金"冻结→划转→解冻"生命周期为什么这样设计？直接扣不行吗？

**解析：** 下买单冻结计价币（available→frozen），不是直接扣（订单可能撤）。成交：frozen→划转给对手→对手 available 增加。撤单：frozen→available（解冻）。直接扣的问题：撤单要还钱（多一次操作且方向反），且下单瞬间扣=用户可用余额跳变体验差，撮合要查可用余额判断够不够。冻结模式 available/frozen 分账，撮合只动 frozen，逻辑清晰且能并发（不动 available）。**陷阱**：冻结要在"下单前校验+写委托+冻结"一个 DB 事务里，否则冻结了没写委托=丢钱（用户余额变少但没单）。资金流水要记冻结/解冻/划转三类。

### Q22. 热点账户（做市商/大户）并发扣款瓶颈怎么解决？

**解析：** 单账户高并发扣款=行锁竞争→TPS 上不去。方案：子账户分片（一个大户拆 N 个子账户，扣款负载均衡到子账户，定时汇总总账）；余额缓存+异步扣（实时记账 Redis/内存，定期对账 MySQL）；乐观锁重试（version）。极端：记账分离（实时记账在 Redis/内存，强一致校验兜底）。**陷阱**：子账户分片要保证总余额不变 + 子账户间划转低频（否则划转本身成热点）。子账户数要按 QPS 动态调整。对账要发现子账户余额和总账偏差自动告警。

### Q23. 热钱包/冷钱包/温钱包的分工？为什么不全放热钱包？

**解析：** 热钱包联网，处理日常提现，余额少（被黑损失可控）。温钱包半联网，热钱包余额低时从温补充，定期归集。冷钱包完全离线（多签+离线签名），存绝大部分资产，提现大额需人工+冷签名。不全放热钱包：热钱包被黑=全站资产被偷（历史上交易所被黑损失数十亿）。分层=风险隔离，被黑只损失热钱包余额。**陷阱**：冷热划转要审计+多签+限额，防止内鬼。热钱包余额监控告警（低于阈值自动从温补充）。提现大额自动转冷签流程，不直接走热钱包。

### Q24. 充值的确认数怎么定？USDT-ERC20 和 USDT-TRC20 为什么不同？

**解析：** 区块链充值要等 N 个确认才算最终（防 reorg/双花）。USDT-ERC20（以太坊）：12-30 确认（出块慢 ~12s + reorg 风险）。USDT-TRC20（波场）：19 确认（出块快 ~3s 但机制不同）。BTC：3-6 确认。确认数=安全 vs 体验权衡。**陷阱**：确认数太少=回滚风险（充了到账后又 reorg=已给用户余额但链上回滚，损失）；太多=体验差（用户等几小时）。各链机制不同要分开配置。还要监控 reorg 深度，超阈值要回滚已到账的充值（要能撤销已加的余额）。

### Q25. 提现地址管理：白名单、地址归集、防内鬼怎么设计？

**解析：** 白名单：用户提现地址必须预先绑定 + 冷却期（绑后 N 小时才能提），防盗号（黑客盗号后绑自己地址要等冷却期，期间用户可发现）。地址归集：充值到用户地址后归集到热钱包（用户地址余额少，降低单点风险+便于管理）。防内鬼：大额提现人工审核 + 多签 + 限额 + 操作日志审计。**陷阱**：归集本身要防被监控地址关联（隐私+链上分析风险）+ gas 成本控制（归集太频繁 gas 高）。归集地址变更要审计。白名单变更也要冷却+二次验证（如邮件/短信）。

### Q26. gas 费谁出？提现的 gas 估算和动态调整？

**解析：** 提现 gas 由用户出（从提现金额扣或单独收 gas 币）。估算：实时查链上 gas price（eth_gasPrice / EIP-1559 base fee+priority），加 buffer 防低估。动态：拥堵时 gas 暴涨，要动态调整提现费率，避免亏损（固定费率会亏——用户按固定费率付，实际 gas 更高=平台贴差价）。**陷阱**：gas 估算偏低=提现卡住待打包（用户体验差+投诉）；偏高=用户多付（投诉）。要用 EIP-1559 的 max fee + max priority fee 机制。还要考虑 nonce 管理（一笔 pending 卡住后续全卡，要用 replace-by-fee 加速）。

## 五、清算结算

### Q27. 逐笔清算 vs 净额清算，交易所用哪个？为什么？

**解析：** 逐笔每笔成交生成资金流水（A 付 X 给 B），明细清晰对账简单，交易所主流。净额按时间窗口净额结算（A 应付 B 净额），适合券商间清算，减少流水。交易所用逐笔：用户要看到每笔成交明细 + 实时余额变化；净额对用户体验差（看不到每笔）。**陷阱**：逐笔流水多→存储和查询压力大，靠 ClickHouse 做分析 + MySQL 分表（按时间）。逐笔流水的"成交驱动余额"模型要保证幂等（TradeID 去重），否则重复消费导致余额错乱。

### Q28. 资金对账：成交流水和余额变动如何对齐？发现不一致怎么办？

**解析：** 对账：成交流水累加 vs 账户余额变动，每 N 时间（如每小时/每日）比对。不一致原因：重复消费未幂等、并发更新丢失（乐观锁失败但没重试）、bug。处理：自动定位差异单 + 人工审核 + 补偿脚本。**陷阱**：对账要"成交驱动余额"单向——即用成交流水重算应有余额 vs 实际余额比对，不能余额反推成交（会掩盖 bug，余额错了发现不了）。对账要分账户类型（用户/做市/平台/手续费收入/热钱包）分别核对。差异要分级（小自动调，大人工）。

### Q29. 穿仓损失怎么处理？保险基金怎么用？

**解析：** 穿仓：合约爆仓时亏损>保证金，用户欠交易所（强平后还负债）。处理：保险基金（累计的部分强平罚金）先垫付；保险基金不足→ADL（自动减仓，盈利方让利）。设计：保险基金要有下限告警 + 穿仓分摊规则明确。**陷阱**：现货一般无穿仓（无杠杆），合约才有；现货的"负余额"靠风控（价格保护 + 余额校验）防。保险基金规模要监控，不足时要及时注资或调整强平罚金比例。保险基金来源透明（公示余额，增强用户信任）。

### Q30. 强平（爆仓）引擎怎么触发？标记价 vs 最新价为什么不同？

**解析：** 触发：维持保证金率 < 阈值→强平。用标记价（mark price，多源指数聚合 + 资金费平滑）判定，不用最新成交价（防操纵/闪崩误爆）。强平：接管仓位→市价平→保证金扣除→剩余返用户/穿仓则保险基金。**陷阱**：闪崩时大量同时强平→流动性危机 + 连环爆仓（强平单推价进一步触发更多强平）→需熔断 + 分批强平（限速）。强平接管价要优于用户破产价（避免扩大损失），用限价强平而非纯市价。

### Q31. T+0 vs T+1 结算对交易所系统设计的影响？

**解析：** 加密现货 T+0（即时成交即时到账可再交易），系统要实时更新余额 + 高并发。传统证券 T+1（次日交收），有结算窗口系统压力小。加密选 T+0：资产流动性强 + 用户体验好；代价=实时清算压力 + 风控实时性要求高（不能延迟清算再发现风险）。**陷阱**：T+0 下充提现也要实时（充值确认后立即可用），资金安全压力更大（充值 reorg 风险 + 实时到账矛盾）。T+0 还要防"双花"——用户充值后立刻提现再 reorg。

## 六、行情系统

### Q32. 深度行情的"聚合"和"脱敏"分别做什么？做市商专线为什么不能聚合？

**解析：** 聚合：把每价位的多笔订单合并显示（按价位档聚合，只显示价位总量），减少推送量。脱敏：隐藏冰山单/隐藏单的部分量，防止做市商/大户被探测真实意图。做市商专线不聚合：做市需要全深度 + 每笔成交 tick + 深度 diff + 私有流，聚合会丢失做市所需的微观信息。但做市商专线要脱敏（隐藏冰山），不能降采样（聚合）。**陷阱**：做市商专线带宽大（逐笔 + 全深度），单独 topic + 独立消费者组，不与用户线争资源。脱敏要做到位（否则做市商仍能探测冰山）。

### Q33. 增量推送 vs 全量快照，什么时候用哪个？断线重连怎么处理 gap？

**解析：** 全量：首次订阅/重连时发当前订单簿快照（量大但准）。增量：正常时只发变化（depth diff，量小）。断线重连：客户端带 last seq 重连；服务端从 seq 缓存回放增量；若缓存不足（gap 太大）→发全量快照重建。**陷阱**：seq 必须连续单调，客户端要校验 seq 连续性发现 gap（收到 seq+2 但没收到 seq+1→请求回放或全量）。服务端 seq 缓存大小要权衡（缓存大覆盖长断线但内存大）。全量快照要和增量 seq 衔接（快照带 base seq，客户端从 base+1 续增量）。

### Q34. seq 为什么不能直接用 Kafka offset？

**解析：** Kafka 一个分区含多 symbol，offset 对某 symbol 不连续（夹着别的 symbol）。聚合后（100ms 聚合成一条）offset 和推送消息非 1:1。多消费者实例各自 offset，无法做"用户感知的全局顺序"。故 seq 单独设计：per symbol 本地原子计数器，独立于 Kafka。**陷阱**：seq 要持久化（周期快照到 Redis）供故障切换续号，否则宕机重启从 0 会导致客户端 seq 倒退触发全量重建（虽不影响正确性但浪费带宽）。seq 跳号可接受（gap 触发全量），但倒退不行。

### Q35. 订阅中心和消费层为什么分开？连接层每台都要消费全量吗？

**解析：** 分开：消费层（Kafka→聚合+seq）CPU 密集；连接层（持 WS）内存/连接密集，职责不同 + 独立扩展。连接层随机：用户连任意一台，该台需持有用户订阅的 symbol 行情。全量消费问题：每台都消费全量=浪费（很多 symbol 用户没订阅）。方案：Kafka③ 广播（每实例独立 consumer group）全量消费，或 Redis Pub/Sub 按需订阅（只订用户要的 symbol）。**陷阱**：Redis Pub/Sub 单线程瓶颈→分片（按 symbol 组分 Redis 实例）或换 NATS JetStream。广播方案每实例都全量消费，symbol 多时带宽浪费，适合 symbol 少或全订阅场景。

### Q36. WebSocket 心跳设计：间隔、超时、重连策略？

**解析：** 心跳：客户端/服务端定时 ping/pong（如 10s），超时（如 30s 无响应）断开。重连：指数退避重连，带 last seq 增量回放。**陷阱**：心跳太频繁=带宽 + CPU 浪费（百万连接 × 10s = 10万/秒 ping）；太疏=僵尸连接占资源。移动端网络切换频繁，重连要快 + 增量回放保体验。服务端要主动清理超时连接（定时扫描）。心跳还要承载"连接存活 + 活跃"双重语义，可用于在线数统计。

### Q37. K线（OHLCV）用什么数据画？为什么不用深度？

**解析：** K线用成交数据（价格/数量/时间）：开高低收=窗口内首/最高/最低/末成交价，量=窗口成交量。不用深度：深度是挂单意愿不是成交，挂单可撤，画 K 线会失真（有人挂了高价单又撤，K 线显示高点但没成交）。多周期：从一个成交流复用算 1m/5m/1h/1d（向上聚合，1m 是基础周期，5m=5 个 1m 聚合），不一周期一管道。实时（推前端，未完成 K 线滚动更新）+ 历史（ClickHouse，完成 K 线落库）。**陷阱**：实时 K 线的"当前 K 线"要随每笔成交更新 open/high/low/close，历史 K 线在窗口结束时定格。

### Q38. 行情推送的 seq 在多实例下如何保证单调？本地原子计数器的局限？

**解析：** 单 symbol 固定实例（靠 Kafka 分区保证同 symbol 路由固定实例）→本地原子计数器单调，零 Redis 开销。局限：实例宕机→新实例需从 Redis 快照恢复 seq 续号（不能从 0）。多 symbol 跨实例：各 symbol 独立 seq，互不干扰。**陷阱**：周期快照（每秒）到 Redis，故障切换从快照+1 续号，可能跳号（可接受，gap 触发客户端全量重建）。但绝对不能倒退（倒退会让客户端增量回放错乱）。实例恢复要快（秒级），否则 seq 长时间不增长影响体验。

### Q39. 时间轮（hashed wheel timer）在行情系统里干什么？为什么用 100ms/10ms？

**解析：** 时间轮：高效定时器，O(1) 调度周期任务。行情聚合按固定周期触发（100ms 用户线 / 10ms 做市商线）。100ms/10ms：人眼/做市商可接受的推送频率；太频繁=带宽爆炸（10ms 推一次全深度），太疏=行情滞后用户抱怨。用户线 100ms 聚合（量小），做市商线 10ms 微聚合（量稍大但做市要细）。**陷阱**：聚合周期要和 seq 推送对齐，避免跨周期 seq 乱（一个周期内 seq 连续）。时间轮槽位大小 = 最小聚合粒度，要大于单次聚合处理时间避免堆积。

## 七、Kafka 应用

### Q40. Kafka 分区设计：为什么按交易对（symbol）分区而不是按用户？

**解析：** 行情/成交流是 per symbol 广播，按 symbol 分区=同 symbol 顺序 + 一个分区一个消费者=串行处理保序。按用户分区：行情是广播（多用户订阅同 symbol），按用户=重复存储 + 无法广播。委托流也可按 symbol 分区（撮合 per symbol）。私有流（用户私有成交）才按 user 分区（用户私有，按 user 路由）。**陷阱**：分区数 ≥ 撮合实例数；热点 symbol 单分区打满要单独 topic 或多分区手动路由（打破 HashPartitioner，用自定义分区器把热点 symbol 散到多分区但同 symbol 内仍有序——实际热点 symbol 一般不拆，靠升级实例解决）。

### Q41. Kafka 的 at-least-once 和消费端幂等怎么配合？

**解析：** Kafka 默认 at-least-once（可能重复投递，rebalance/offset 提交失败时）。消费端幂等：用业务 ID（TradeID/订单ID）去重，INSERT IGNORE / 唯一索引 / Redis SETNX。配合：at-least-once 保证不丢，幂等保证不重，合起来=exactly-once 语义（实际效果，非 Kafka 原生 EOS）。**陷阱**：幂等键要全局唯一且稳定（贯穿全链路）；不能依赖 Kafka offset 做幂等键（offset 不跨 rebalance 稳定且业务无关，offset 提交了但消息可能被其他消费者重消费）。幂等要在"处理+标记"同事务里，否则处理了没标记=重复处理。

### Q42. consumer group rebalance 时怎么保证不丢不重？

**解析：** rebalance：分区重分配给新消费者，可能重复消费（旧消费者未提交的）或漏消费（已提交但未处理完）。不丢：处理完再提交 offset（手动提交，commit_interval=0 或处理成功后同步提交）。不重：幂等消费。**陷阱**：自动提交（commit_interval>0）可能"已提交未处理"→rebalance 时丢消息；要权衡延迟和可靠性（手动提交频率高=开销大）。rebalance 期间消费暂停（stop-the-world），高负载时影响延迟，要缩短 rebalance 时间（session timeout 调小、partition 数合理）。

### Q43. outbox + Kafka 写事务边界：为什么不直接 Kafka 事务？

**解析：** Kafka 事务（transactional producer）只保证 Kafka 内 exactly-once（消费-处理-生产链路），不能跨 DB（DB 事务和 Kafka 事务是两个独立事务）。outbox：DB 事务（业务表 + outbox 表）原子，再异步发 Kafka，实现跨 DB+Kafka 的一致性。Kafka 事务用于"消费-处理-生产"流处理链路（streams），不适合 DB+Kafka。**陷阱**：outbox 发 Kafka 可能重复（发成功但 ack 丢失）→消费幂等兜底。outbox 轮询有延迟，上 Debezium 监 binlog 实时发 Kafka（CDC）可降到秒级甚至更低。

### Q44. Kafka 分区数怎么选？太多太少各有什么问题？

**解析：** 太少：吞吐瓶颈（单分区串行，热点 symbol 打满）。太多：开销大（broker 元数据 + 消费者协调），rebalance 慢，端到端延迟可能增加（分区多→消费者多→协调开销）。经验：分区数 = 预期峰值吞吐 / 单分区吞吐，留 buffer；symbol 分区至少 1，热点可单独多分区。**陷阱**：分区数后期只能加不能减（Kafka 限制，减分区会破坏顺序），初期规划好。分区数过多还会增加 broker 内存（每分区副本有索引），一般单 broker 分区数上限几千。

### Q45. Kafka key 路由（HashPartitioner）的作用和陷阱？

**解析：** key 路由：相同 key（如 symbol）→固定分区→同 key 顺序保证。作用：保证同 symbol 的委托/成交顺序，消费者按分区串行。**陷阱**：key 分布不均（热点 symbol）→分区倾斜（某分区打满，其他空闲）。解决：热点 symbol 单独 topic 或多分区手动路由（但会破坏"同 key 单分区"顺序保证，需消费者端按 key 内 seq 保序）。无 key（轮询分区）无顺序保证，不适合撮合顺序敏感场景，适合日志/指标。

### Q46. Kafka 消费者的 offset 提交：自动 vs 手动的取舍？

**解析：** 自动（commit_interval）：简单，但有"已提交未处理"丢消息风险（rebalance 时消息已提交 offset 但还没处理完）。手动：处理成功后提交，不丢，但提交频率高=开销大 + 延迟（同步提交阻塞）。折中：批量提交（处理 N 条后提交）+ 异步提交（不阻塞但可能重复消费）。**陷阱**：处理失败不提交→下次重消费（at-least-once）+ 幂等。异步提交 + 手动同步提交结合：正常异步，rebalance 前同步提交确保不丢。

### Q47. Kafka 在交易所里同时承载多个 topic（行情/委托/成交/私有），会不会互相影响？

**解析：** topic 独立，各自分区 + 消费者组，逻辑隔离。物理共享 broker：高负载 topic（行情 tick 高频）可能影响其他（IO/CPU 争抢，页缓存竞争）。解决：独立集群或资源隔离（broker 分组，关键 topic 用独立 broker）。分区迁移：broker 故障时分区 leader 切换，瞬时延迟峰值（controller 重新选 leader）。**陷阱**：关键路径（委托）和非关键（行情归档）最好分集群，避免行情峰值影响下单。Kafka 集群监控要分 topic 指标，不能只看整体。

## 八、存储

### Q48. MySQL / ClickHouse / Redis 在交易所的分工？为什么不能只用一个？

**解析：** MySQL：业务凭证（委托/成交/账户余额），ACID 强一致，事务。OLTP，吞吐有限（单机几万 TPS）。ClickHouse：分析（K线/历史行情/风控离线），列存 + 高压缩 + 聚合快，OLAP（亿级数据秒级聚合）。Redis：热缓存（用户余额/seq/限频/会话），低延迟 KV（μs）。不能只用一个：MySQL 抗不住分析聚合（全表扫描慢）；ClickHouse 不适合事务（无强一致 + 不擅更新）；Redis 不持久化不可靠（宕机丢数据）。**陷阱**：三者要 CDC/缓存一致性保证同步，数据流向：MySQL 真相源 → CDC → ClickHouse，Redis 缓存 MySQL 热数据。

### Q49. MySQL→ClickHouse 的 CDC 用 binlog 怎么做？为什么不一库双写？

**解析：** CDC：监听 MySQL binlog（canal/Debezium/自研 go-mysql），解析行变更写 ClickHouse。不双写：双写=两个写点，需保证一致（难，跨库事务性能差），且失败处理复杂（一库写成功另一库失败怎么补偿）。CDC 单写源（MySQL）=真相，ClickHouse 是异步副本，最终一致（秒级延迟）。**陷阱**：CDC 延迟（秒级）+ binlog 顺序保证（按 binlog position 顺序写 CH）；ClickHouse 写入要批量 + 合并（攒一批写，减少 part 数）。成交 append-only 是 CDC 友好（只插不改），订单状态机要 ReplacingMergeTree + version 处理更新。

### Q50. ClickHouse 的 ReplacingMergeTree + version 为什么适合订单状态？

**解析：** 订单状态会变（NEW→FILLED），ClickHouse 追加写不支持直接更新。ReplacingMergeTree：同主键（订单 ID）按 version 取最新，后台合并去重，模拟"更新"。version：订单状态机版本号，保证取最新状态。**陷阱**：合并是异步的，查询时可能同时读到旧 + 新行（未合并），需用 `FINAL` 关键字或去重查询（`argMax`）保证取最新。FINAL 性能差，一般配合业务容忍（实时查询用 MySQL，分析用 CH）。ReplacingMergeTree 不保证实时去重，只保证最终。

### Q51. ClickHouse 的 MergeTree 为什么不适合高频更新？

**解析：** MergeTree 追加写 + 后台合并，更新=新插一行 + 合并替换，写放大严重（一次更新 = 一条新 part）。高频更新（如订单状态频繁变）→大量 part 不合并→查询慢 + 存储膨胀。替代：ReplacingMergeTree（按主键去重）或 CollapsingMergeTree（sign 抵消，+1/-1 行）。**陷阱**：余额这类高频变更不适合存 ClickHouse，存 MySQL/Redis。ClickHouse 的设计哲学是"写一次读多次"，适合 append-only（成交、日志、行情）。

### Q52. 热冷数据分离怎么设计？历史成交存哪？

**解析：** 热（近 N 天，查询频繁）：MySQL 热表 / Redis 缓存 / ClickHouse 热分区（内存或 SSD）。冷（历史，偶尔查）：ClickHouse 全量 + 归档存储（S3/对象存储）。成交：实时入 MySQL（凭证）+ CDC 到 ClickHouse（分析）；历史查询走 ClickHouse。**陷阱**：MySQL 老数据要定期归档（按月分表/删旧），否则表越来越大拖慢查询 + 备份慢。归档要平滑（用户查半年前成交不能报错），靠 ClickHouse 统一历史查询接口。冷热分层让 MySQL 表小、查询快。

### Q53. 分库分表：按什么分？账户/成交/委托的分片键？

**解析：** 账户：按 user_id 分片（用户隔离，查询自己的余额快）。成交：按 symbol + 时间 或 trade_id 分片（查询多按 symbol + 时间，如"BTC/USDT 今日成交"）。委托：按 user_id（用户查自己的单）或 symbol（撮合查询）——矛盾，需冗余（写两份按不同键）或按查询模式选主键。**陷阱**：跨片查询（如全局成交额统计）难，要 ClickHouse 做分析弥补（ClickHouse 不分片或分布式表）。分片键选错会导致热点（如按 symbol 分但 BTC 是热点）。

### Q54. Redis 缓存用户余额，和 MySQL 怎么保证一致？

**解析：** 读：先 Redis 后 MySQL（Redis miss 回填）。写：先 MySQL 后删 Redis（cache aside，删除而非更新避免并发覆盖）；或先删后写 + 延迟双删。余额变更频繁→不能每笔都回写 Redis（压力），用本地缓存 + 批量同步。**陷阱**：并发"读 miss 回填"和"写"竞态→用延迟双删（写后延迟再删一次）或版本号。极端强一致场景（提现）直接读 MySQL 跳过 Redis。缓存击穿（热 key 过期）用互斥锁或不过期 + 异步刷新。

## 九、风控

### Q55. 下单前风控为什么要毫秒级？哪些规则能放这层，哪些不能？

**解析：** 下单前风控在用户 WS→撮合的关键路径，慢=拖累全站下单体验（用户感知延迟）。能放：余额/冻结、价格保护（胖手指偏离）、限频、单笔量上限、权限、自成交预检——单值快查（本地缓存 + Redis）。不能放：复杂模式检测（撤单率/操纵）——需跨多事件 + 时间窗口，放实时层异步。**陷阱**：下单前规则要"轻"（本地缓存 + Redis 快查，不查 DB），重规则异步。风控超时降级策略要明确（放行 + 告警 vs 拒绝，看风险偏好）。

### Q56. 价格保护（胖手指）阈值怎么定？偏离市场价多少拒绝？

**解析：** 阈值：偏离当前 mid 价 ±X%（如 5%-10%）拒绝。X 要平衡：太小=正常波动被误拒（用户体验差，正常下单失败）；太大=胖手指损失（用户误下大单成交损失）。动态：波动大时放宽，平稳时收紧。**陷阱**：用 mid 还是 last price？mid 更稳（防 last 被单笔操纵）；参考第三方价更准（防本所薄盘 mid 失真）。做市商账号要单独配置（做市需要在偏离处挂单提供流动性），但价格保护仍要保留（防做市 bug）。

### Q57. 自成交预防：Pre-trade 和 Realtime 两层各做什么？

**解析：** Pre-trade：下单前检查用户现有挂单，若会和本单成交→拒绝/修改。本地查快（查用户订单簿缓存）。Realtime：实时发现自成交（pre 漏的或并发，如两端同时下单）→取消成交/标记。离线：跨账户关联自成交（同 IP/设备/资金关联账户互敲，洗盘）→挖掘 + 冻结。**陷阱**：Pre 只能查同账户（快），跨账户靠离线（实时难判定关联，且关联关系是图，难实时算）。自成交预检要快否则拖累下单。洗盘判定要谨慎（正常做市也可能自己挂的买卖单被自己成交，要区分意图）。

### Q58. 操纵检测（spoofing/layering）为什么必须用 Flink CEP，不能用 Go 逐条？

**解析：** spoofing：大单挂出→价格移动→撤（不 intend 成交），需跨 order/cancel/trade 多事件 + 时序模式。layering：多档挂单→价格移动→撤。Go 逐条难写（要持有跨事件状态 + 时序窗口 + 复杂 pattern，代码复杂易错）。Flink CEP（PatternStream）专为时序模式设计，声明式定义 pattern（"挂大单 → 价格移动 → 撤"），状态管理 + 窗口内置。**陷阱**：spoofing 判定模糊（正常挂撤也多），实时难→告警 + 人工，非硬拦（误杀正常做市）。离线挖掘关联 + 模型辅助判定。

### Q59. 哪些风控用 Flink，哪些用 Go+Redis？分界原则？

**解析：** Go+Redis（下单前，单事件单值查表）：余额/价格保护/限频/权限/保证金——毫秒级，本地查。Flink（多事件时序 CEP + 窗口聚合）：spoofing/layering/撤单率/对敲/熔断/偏离外部/AML 链路——秒级，消费 Kafka 流。原则：一条消息能判完→Go；要跨多条消息 + 时间窗口 + 时序模式→Flink。离线复盘 → ClickHouse。**陷阱**：别用 Flink 做下单前逐条过滤（延迟 + 复杂，下单前要毫秒级）。Flink 成本不低（JVM 集群 + checkpoint + 运维），只为复杂 CEP 和大规模窗口聚合用，简单窗口用 Go + Redis ZSET 够。

### Q60. 价格熔断怎么设计？涨跌幅多少触发暂停？

**解析：** 熔断：N 分钟内价格涨跌超 X%（如 5 min ±10%）→暂停交易若干分钟。分级熔断：5% 警告/10% 暂停/15% 长暂停。触发价用标记价（防操纵），非单笔成交价（单笔可被操纵触发误熔断）。**陷阱**：熔断期间委托怎么办（撤/挂/转限价）要明确告知用户；恢复后防连环波动（分批恢复 + 价格限制）。熔断要区分"正常波动"（市场整体下跌）和"异常"（本所被操纵），前者不熔断（跟着市场走），后者熔断。

### Q61. 限频怎么设计？按 user 还是按 IP？滑动窗口怎么实现？

**解析：** 按 user（API key）+ IP 双维度（防盗号刷 + 防未登录刷）。滑动窗口：Redis ZSET（score=时间戳，value=唯一请求 ID），`ZCOUNT` ZSET 内 [now-window, now] 元素数，超限拒。权重：不同接口权重不同（下单重，查询轻）。**陷阱**：做市商账号放宽限频（高频做市需要），但要单独配置 + 审计（防滥用）。滑动窗口 ZSET 要定期清理过期元素（ZREMRANGEBYSCORE）防膨胀。分布式限频（多实例）要 Redis 集中（本地限频不准，用户请求分散到多实例）。

### Q62. 风控宕机怎么办？降级策略？

**解析：** 风控宕机=要么交易停（拒所有下单，保安全但停摆），要么裸跑（放行 + 告警，保可用但有风险），都不好。HA：风控引擎主备。降级：下单前风控超时→默认放行 + 告警（保可用，风险可控）或默认拒绝（保安全），看风险偏好，一般选"放行 + 强告警"（风控宕机不该让交易停）。**陷阱**：风控不能成单点瓶颈（慢=拖累下单），下单前风控要 HA + 超时降级。实时/离线风控宕机不影响下单（异步），只影响监控，但要尽快恢复。

## 十、做市

### Q63. 做市和套利的本质区别？为什么做市有库存风险而套利"近无风险"？

**解析：** 做市：单所双边挂单（bid<ask），被动 maker，赚买卖价差，承担库存风险（单边成交堆积，价格逆向亏）。套利：跨所/跨品对冲，赚价差，腿对冲≈无风险（腿风险是最大残余风险，但比做市库存风险小）。动机：做市=价差提供者（spread provider，提供流动性）；套利=价差消除者（spread eliminator，消除跨市场价差）。**陷阱**：都用到对冲技术，但动机不同；做市靠震荡（双边成交赚价差），套利靠价差（跨市场定价不一致）。做市和套利可共享底层（行情/对冲/下单通道），策略层分离。

### Q64. Avellaneda-Stoikov 做市模型的核心？库存如何影响报价？

**解析：** 核心：最优报价 mid ± spread/2，spread 随库存偏离和波动率调整。库存多→偏移报价（多仓则降价卖/少买，引导减仓）。公式（简化）：保留价 `r = s - q·γ·σ²·(T-t)`（q 是库存，γ 风险厌恶，σ 波动率，T-t 剩余时间），最优买/卖价 = `r ± (γσ²(T-t) + ln(1+γ/κ))/2`（κ 成交率参数）。**陷阱**：参数（γ/σ/κ）难调，需历史数据拟合 + 在线更新；趋势市失效（单边堆积，模型假设均值回归不成立）。要做库存止损（超限强制减仓）+ 趋势检测降仓。

### Q65. pegging（锚定）做市怎么跟随第三方价格调整本所行情？

**解析：** 不能直接改撮合价（合规，撮合价由订单簿决定），靠挂单跟随：消费第三方参考价 P_ext→bid/ask = P_ext ± spread/2→挂单→成交后跨所对冲消除库存。spread 含延迟溢价（P_ext 到本所成交间的价格漂移风险）+ 补偿 + 费 + 库存风险。**陷阱**：延迟套利风险（看到 P_ext 到本所挂单成交间，外部价已变，对冲时亏损）；跨所对冲执行风险（外部所深度不足/滑点）。场景：新币开盘（无本所价，跟随外部）、异常检测（本所偏离外部告警）、指数价构建。

### Q66. 做市商专线和用户专线的区别？为什么做市要全深度+逐笔？

**解析：** 用户专线：聚合 + 脱敏，100ms 推送，省带宽 + 隐私（不让用户互相探测意图）。做市专线：全深度 + 逐笔成交 tick + 深度 diff + 私有流，10ms，不聚合（但脱敏冰山，隐藏隐藏单）。原因：做市需微观信息（每笔成交、深度变化、订单流）决策报价，聚合丢失关键信息（100ms 聚合看不出瞬时变化）。**陷阱**：做市专线带宽大（逐笔 + 全深度 + 私有），独立 topic + 消费者组，不与用户线争资源。脱敏要做到位（否则做市商能探测冰山单获不公平优势）。

### Q67. 做市在窄震荡和单边趋势下盈亏为什么相反？

**解析：** 窄震荡（黄金场景）：双边频繁成交 + 库存对冲（涨时卖出的仓位跌时买回，库存自动平衡），价差收入 > 库存损失，赚。单边趋势（坟墓场景）：单边成交堆积（趋势方向一直吃单边，如持续上涨时卖单一直被成交，库存变空头 + 价格继续涨=逆势亏损），库存堆积 + 逆势价格，亏。策略：库存管理（偏移报价减仓/对冲）控制趋势风险。**陷阱**：做市不是"低买高卖"（那是投机，方向赌注），是"同时双边挂单赚价差"——成交时一边买一边卖，赚 bid-ask 差。趋势市做市要降仓位或暂停。

### Q68. 做市策略引擎的闭环：消费→报价→下单→对冲→循环，哪环最易出问题？

**解析：** 闭环：消费（行情 + 私有报告）→策略决策→报价→下单（到撮合）→对冲（跨所）→回消费（看成交结果调整）。易出：对冲执行（跨所延迟 + 滑点 + 腿风险，对冲失败=裸敞口）；报价参数（趋势市失效，参数没及时调整）；延迟（行情滞后导致决策过时，按旧价报价成交即亏）。**陷阱**：对冲失败=裸敞口，要有止损 + 敞口监控 + 人工介入。报价要根据实时库存动态调整（不能固定 spread）。延迟监控（行情新鲜度，超时不用旧数据决策）。

## 十一、延时/性能

### Q69. Go 做交易所撮合够不够？什么时候要上 C++/Rust？

**解析：** Go 够：加密 ms 级延迟容忍，Go 并发（goroutine）+ 生态好，开发快，团队易招。上 C++/Rust：延迟成亏损驱动时（μs 级 HFT，做市/套利利润被延迟吃掉），Go 的 GC STW（虽 ms 级但仍抖动）+ 运行时开销（调度/边界检查）成瓶颈。判断：延迟 P99 是否影响做市/套利利润；若否，Go 性价比高。**陷阱**：别为"快"上 C++——先优化 Go（GC 调优 GOGC + sync.Pool + CPU pinning + 减少分配 + 无锁），Go 优化到极限仍不够再考虑。C++/Rust 开发慢 + 团队贵 + 调试难，成本要算清。

### Q70. Go GC 调优：GOGC、sync.Pool、CPU pinning 各解决什么？

**解析：** GOGC：触发 GC 的堆增长比例，调大（如 GOGC=200）触发频率低（STW 少），调小（GOGC=50）内存回收勤（占用低）。撮合调大 + 控制堆（避免堆膨胀）。sync.Pool：复用对象（如订单结构体）减少堆分配=减少 GC 压力（分配是 GC 根因）。CPU pinning：GOMAXPROCS + 绑核 + 隔离 GC 线程到独立核，避免调度抖动（GC 线程不抢占撮合核）。**陷阱**：GOGC 调太大=OOM 风险（堆不回收）；要监控 + 压测。sync.Pool 对象在 GC 时会被清空（不能依赖持久），适合短期复用。runtime.GC 模型变了（Go 1.19+ 软删除），要看版本。

### Q71. 无锁队列（lock-free）在撮合里干什么？比 mutex 快多少？

**解析：** 撮合单 symbol 单线程本来无锁，但跨线程传递（如撮合→行情推送线程）用无锁队列（MPSC ring buffer，disruptor 思想）避免锁竞争。比 mutex：无 contention 时差不多（mutex 无竞争时 cheap），高 contention 时无锁吞吐高且延迟稳定（无抖动，不排队等锁）。**陷阱**：无锁实现难（内存序 ABA 问题，要用 atomic + CAS + memory order），一般用成熟库（不自造）。无锁队列容量固定（ring buffer），满了要处理策略（阻塞/丢弃/扩容）。调试难（数据竞争难复现）。

### Q72. 序列化对延迟的影响？为什么撮合内部不用 JSON？

**解析：** JSON 解析慢（反射 + 字符串）+ 体积大（字段名冗余），μs 级路径不能用。撮合内部用二进制（protobuf/flatbuffers/自定义 struct 直接传内存引用）。跨进程：protobuf（紧凑 + 快）；同进程：直接 struct 引用（零拷贝，传指针）。**陷阱**：外部 API（用户）仍 JSON/WebSocket 文本（通用 + 调试方便），在网关层转二进制（网关解析 JSON→内部二进制）。flatbuffers 零拷贝反序列化（适合行情广播，多消费者共享同一 buffer）。自定义二进制要处理版本兼容（字段加减）。

### Q73. 零拷贝（zero-copy）在哪些环节用？

**解析：** 行情推送：Kafka 消费→聚合→WS 推送，用 sendfile/io_uring 减少内核态拷贝（数据从页缓存直接到 socket，不经用户态）。大消息：避免反序列化+再序列化，直接传字节（flatbuffers）。**陷阱**：零拷贝要求数据不可变 + 生命周期管理（多消费者共享 buffer 时不能被任一消费者修改，且要防止释放后访问，用引用计数或 arena）。Go 的 io.Copy 底层用 sendfile，但 WS 帧封装会破坏零拷贝（要加帧头）。零拷贝和 protobuf 反序列化矛盾（反序列化要读内容），flatbuffers 解决（零拷贝读）。

### Q74. 线程模型：Reactor vs Proactor？撮合用什么？

**解析：** Reactor：事件驱动（epoll/linux），适合 IO 密集（网关/推送，多连接复用线程）。Proactor：异步 IO（IOCP/Windows），完成回调。撮合：单线程 busy-loop（CPU 密集，无 IO 等待，自旋处理），不是 Reactor（Reactor 有 epoll 等待开销）。网关：Reactor（epoll + goroutine，Go runtime 自带 netpoll）。**陷阱**：撮合线程不能阻塞 IO（会卡撮合，撮合要持续处理订单），所有 IO（落 MySQL/Kafka）异步旁路。busy-loop 占满 CPU（要绑核隔离，否则影响其他服务），适合专用实例。

## 十二、高可用

### Q75. 主备切换的脑裂场景和 fencing token 怎么防？

**解析：** 脑裂：网络分区→主备都认为自己是主→双写（重复成交/双扣资金）。fencing：备升主带递增 token（epoch），下游（资金/行情/Kafka 写）只认最新 token；旧主 token 落后→写被拒→自动降级。token 来源：分布式协调（etcd/zk 的 lease revision）或单调时钟。**陷阱**：fencing 要覆盖所有下游，漏一个就脑裂（如覆盖了资金但漏了 Kafka 写，旧主仍能写 Kafka 导致重复成交推送）。token 校验要同步（下游收到旧 token 写立即拒，不等）。fencing token 要持久化（备升主后 token 持久化，宕机重启不回退）。

### Q76. lease 续约失败到备升主的延迟怎么最小化？

**解析：** TTL 太大→故障检测慢（主宕机后等 TTL 才升主）；太小→误判（网络抖动误升主=脑裂）。优化：心跳频繁（续约间隔小，如 1s）+ TTL 适中（如 3s）；故障检测用多数派（不只心跳，配 zk/etcd quorum，多数节点同意才升主，降低误判）。**陷阱**：网络抖动误判→频繁切换=抖动（主备反复切换，状态迁移成本高），要加入稳定窗口（连续 N 次失败才升主）+ 人工介入开关（关键服务切换要人工确认）。升主延迟 vs 误判是 trade-off，加密交易所选秒级延迟 + 误判容忍低（宁可慢点也别脑裂）。

### Q77. 多机房容灾怎么设计？撮合主备能跨机房吗？

**解析：** 跨机房：延迟大（同城几 ms，跨城几十 ms），撮合主备跨机房=每次写跨机房延迟（主写→备同步），撮合扛不住（撮合要 μs/ms 级）。方案：撮合主备同机房（低延迟）；跨机房做异步副本（灾备，非实时切换，RPO>0）。异地多活：业务层多活（如行情/查询/提现受理），撮合层单点 + 灾备（同城主备 + 异地异步副本）。**陷阱**：跨机房切换 RPO>0（有数据丢失，丢失窗口=异步同步延迟），要明确容忍度。同城主备跨机房（同城延迟 ms 级可接受）是折中，但要 fencing 防脑裂。

### Q78. 限流（Sentinel/自研）在交易所各层怎么部署？

**解析：** 网关层：全局 + 接口级限流（防 DDoS，按 IP/总 QPS）。业务层：按 user/API key 限频（风控，防刷单）。资源层：DB/Redis 连接池 + 熔断（防雪崩，下游故障时快速失败保护上游）。策略：快慢限流（快速限频 + 慢速配额，如秒级限频 + 日级配额）。**陷阱**：限流要分级（全局/接口/用户/资源），否则正常用户被限（如全局限流过严，大户一单触发全站限流）。限流规则要可热更新（大行情时临时放宽）。熔断要区分关键路径（撮合依赖的资金，熔断要降级而非直接失败）。

### Q79. 降级策略：行情系统挂了交易还能继续吗？

**解析：** 行情挂=用户看不到价格，但撮合（内存订单簿）独立，交易可继续。降级：行情降级到"最后可用快照" + 告警；撮合继续用内部 mid（内存订单簿的最优价）维持。**陷阱**：依赖行情的风控（价格保护）要降级（用缓存 mid 或暂停高风险单，如市价单）。K线/深度推送暂停（告知用户重连）。行情恢复后要回填缺失数据（从 Kafka 重放）。交易和行情解耦设计是关键——行情只是撮合的"视图"，挂了不影响撮合本质。

### Q80. 熔断（circuit breaker）在服务调用链怎么用？

**解析：** 下游服务（如风控/资金/行情归档）故障率超阈值→熔断，快速失败 + 降级，防止雪崩（上游等下游超时耗尽线程）。半开（half-open）：探测恢复后逐步放流量（先放 1 个请求试，成功则恢复，失败则继续熔断）。**陷阱**：熔断要区分关键路径（撮合依赖的资金服务，熔断要降级——如资金冻结用本地缓存余额兜底——而非直接失败导致下单全失败）和非关键（行情归档，熔断直接丢弃）。熔断阈值要合理（过高不触发，过低误熔断）。熔断状态要可监控 + 人工重置。

## 十三、网关/API

### Q81. WebSocket 网关如何鉴权？API key 签名怎么做？

**解析：** 连接时带 API key + 签名（HMAC-SHA256(timestamp + params, secret)）。timestamp 防重放（窗口 ±N 秒，如 ±5s，过期拒绝）。**陷阱**：secret 不能前端存（用托管/后端代理签名）；签名校验在网关 + 风控双校验（网关校验防伪造，风控校验防异常调用）。nonce 防重放（每次请求递增 nonce，服务端记已用 nonce 拒重复）。时间同步要保证（NTP，否则签名因时间戳偏差被拒）。

### Q82. REST 和 WebSocket 在交易所的分工？

**解析：** REST：下单/撤单/查询（请求-响应，需要确认成功/失败）。WebSocket：行情推送 + 私有成交推送（单向高频流，服务端推客户端）。下单为何 REST：要立即确认成功/失败（订单状态），WS 推送难保证请求确认语义（双向 WS 需 ack 机制，复杂）。**陷阱**：有人用 WS 下单（双向 WS，低延迟），但需 ack 机制（消息 ID + 服务端 ack），复杂且难保证可靠投递；主流 REST 下单 + WS 推送。查询类高频（如查订单状态）可走 WS 私有推送（服务端主动推状态变化，省轮询）。

### Q83. 负载均衡：WS 长连接怎么 LB？为什么不能简单轮询？

**解析：** WS 长连接：一旦建立持续，LB 只在连接建立时分配，之后固定到某实例。不能简单轮询：连接时长不一→实例负载不均（有的持几万连接，有的几千，老连接不断新连接累积）。方案：最少连接数 LB（L7 LB 按 connection count 分配）+ 连接迁移（重连时再均衡，主动断开超量连接让其重连）+ 健康检查（实例挂了连接迁走）。**陷阱**：单机连接数上限（文件描述符/内存）→要预估 + 水平扩展。LB 要支持 WS（L7，能处理 Upgrade 头），L4 LB 不行（不解析 HTTP）。Graceful shutdown（实例下线前主动断开连接让其重连，避免丢连接）。

### Q84. 灰度发布怎么做？撮合引擎能灰度吗？

**解析：** 灰度：按用户/symbol/比例分流流量到新版本。撮合灰度难：状态有延续（订单簿内存状态，不能简单分流——新版本没有旧版本的订单簿）。方案：新 symbol 用新版本灰度（新币上线直接用新版本，不影响存量）；或停机切换（维护窗口，老版本停 + 数据迁移 + 新版本起）。**陷阱**：撮合灰度要数据迁移（订单簿状态从老版本导到新版本）+ 回滚预案（新版本出问题能切回老版本 + 状态回迁），比无状态服务难。行情/网关等无状态服务灰度简单（按比例分流）。撮合灰度要充分测试（影子流量——新版本旁路处理真实流量比对结果，不真实下单）。

### Q85. API 版本管理：v1/v2 共存怎么设计？

**解析：** URL 路径分版本（/v1/order /v2/order），网关路由到不同版本服务。v1 废弃要提前公告（如 3 个月）+ 过渡期 + 监控使用率（低于阈值才下线）。**陷阱**：版本间字段/语义差异要兼容（v2 字段更全，v1 用默认值）；老版本 bug 仍要修（维护成本，但安全 bug 必须修）。版本演进要文档化（changelog，告诉用户变化）。废弃要分阶段（deprecation warning → 限制 → 下线），不能直接下线（用户来不及迁移）。

## 十四、合约

### Q86. 指数价、标记价、最新价三个价格的区别？为什么要三个？

**解析：** 最新价：本所最新成交价，反映本所实时，易操纵（薄盘单笔大单可推价）。指数价：多所现货价加权平均（如取 Binance/OKX/Coinbase 现货价中位数或加权），反映市场公允，锚定用。标记价：指数价 + 资金费平滑，用于强平判定 + 未实现盈亏计算，防操纵/闪崩误爆。三个：最新给用户看成交（直观），指数给公允锚（合约价不该偏离指数太远），标记给强平判定（防闪崩连环爆）。**陷阱**：强平用标记价不用最新价（防本所被操纵触发连环爆仓）。指数价源要分散（不能只依赖一个所，否则该所被操纵指数也失真）。

### Q87. 资金费率（funding rate）怎么算？为什么永续要收资金费？

**解析：** 永续无交割日，靠资金费让合约价回归指数（否则合约价可长期偏离指数）。资金费 = 持仓量 × 资金费率，正费多头付空头，负费反之。费率 = clamp(溢价 / 利率, ±上限)，溢价 =（合约价 - 指数价）/ 指数价（合约价>指数→多头付空头，鼓励做空拉回）。每 N 小时结算（如 8h）。**陷阱**：结算瞬间价格可能跳（套利者平仓）。资金费套利存在（合约价>指数时空头+现货多收资金费），但有价差风险（非无风险）。资金费率有上限（±0.75% 等），极端行情 clamp。

### Q88. 保证金 isolated vs cross 的区别？各适合什么？

**解析：** isolated（逐仓）：每仓独立保证金，爆仓只影响该仓，风险隔离，适合单仓策略（如明确止损的短线）。cross（全仓）：全仓共享保证金，盈利仓补亏损仓，抗波动强（一时浮亏不爆）但一爆全爆（连环风险）。**陷阱**：cross 看似安全实则连环爆风险（一个大亏仓拖垮全仓）；用户要按策略选。做市商常用 cross（多品种对冲，整体风险可控）。系统要支持用户切换（但切换有条件，如无持仓时切）。保证金计算要实时（标记价 + 未实现盈亏）。

### Q89. 强平后的保证金怎么分配？保险基金怎么累积？

**解析：** 强平：接管仓→市价平→若盈利返用户（剩余保证金），若亏损扣保证金。穿仓（亏>保证金）：保险基金垫付。保险基金来源：强平时罚金（部分保证金划入基金，即"社会损失"前置）+ 平台注资。**陷阱**：保险基金规模要监控，不足时要及时注资或调整强平罚金比例。保险基金下限告警→触发 ADL。保险基金来源透明（公示余额，增强用户信任）。强平接管价要优于用户破产价（避免扩大损失），用限价强平（穿仓风险=成交价差）而非纯市价（滑点大）。

### Q90. ADL（自动减仓）什么时候触发？对盈利方公平吗？

**解析：** 保险基金不足 + 穿仓→ADL，按盈利方杠杆/盈亏排序强平盈利仓让利（让盈利方放弃部分利润弥补穿仓损失）。不公平但必要（否则穿仓损失无人承担=平台亏，平台亏则跑路风险）。**陷阱**：ADL 要提前告知（用户能看到被 ADL 风险）+ 排序透明（按保证金率排序，保证金率低的先被 ADL）。用户可用低杠杆（高保证金率）降低被 ADL 概率。ADL 是最后手段，正常靠保险基金覆盖。ADL 触发要公告（市场透明）。

### Q91. 永续合约的资金费能套利吗？资金费套利的风险？

**解析：** 套利：合约价>指数时做空合约+现货多，收资金费（多头付空头）。风险：合约价回归前价差波动（合约价继续涨，空单浮亏可能超过资金费收益）+ 资金费率反转（溢价变贴水，费率转负）+ 现货对冲执行风险（现货深度/滑点）。**陷阱**：不是无风险（价差风险大），是"资金费收益 vs 价差风险"权衡。资金费率有上限 clamp，极端时收益有限。结算周期内费率可变（按瞬时费率估算，实际结算时可能已变）。

## 十五、第三方行情采集/套利

### Q92. 第三方行情采集：多源（Binance/OKX/Coinbase）怎么融合？

**解析：** 多源 WS/REST 采集→去重 + 校验 + 融合。融合：中位数/加权（按成交量）取参考价，去极值（剔除偏离过大的源，可能该所异常或被操纵）。故障切换：某源断→剔除，剩余继续（多源冗余）。**陷阱**：源之间价差（套利空间）+ 延迟不一致→以时间对齐（各源带时间戳，取同一时刻的价）。源的权重动态调整（成交量大的所权重高，但要防单一所主导）。采集服务本身要 HA（多实例 + 故障切换），否则单点故障导致参考价缺失。

### Q93. 跨所对冲套利的"腿风险"是什么？怎么降低？

**解析：** 腿风险：两腿成交不同步（A 腿成了 B 腿没成/价格已变），敞口暴露（只有一边仓位，市场反向即亏）。降低：先流动性差的腿后流动性好的腿（先在差所成交，再到好所对冲，好所成交概率高）；同市价单尽量同时（但不可能真同时）；用 limit + IOC 控制滑点（限定成交价，超出不成交则整单废）。**陷阱**：腿风险是套利最大残余风险，纯"无风险套利"实际不存在（总有腿风险 + 成本）。高频竞争下机会稍纵即逝（看到价差到成交间价差消失），要低延迟 + 自动化。

### Q94. 三角套利的逻辑和实现难点？

**解析：** 逻辑：A→B→C→A 循环（如 USDT→BTC→ETH→USDT），价差>手续费则盈利。难点：三腿同步成交（一腿失败全废，敞口暴露）+ 汇率计算实时（每腿价实时变）+ 各所深度滑点（大单滑点吃掉利润）。**陷阱**：理论价差和实际成交滑点差大（小价差被滑点吞）；高频竞争激烈（套利机会被多个 bot 争抢，先到先得）。要原子性（三腿要么全成要么全废，靠 IOC + 失败回滚）+ 极低延迟。三角套利利润薄（需大资金 + 高频）。

### Q95. 套利成本公式？什么条件下套利才盈利？

**解析：** 成本 = 价差 − 手续费（双边/多边）− 滑点（大单深度）− 转账费（跨所搬币）− 资金成本（占用资金的时间价值）− 风险溢价（腿风险/时间风险）。盈利条件：价差 > 上述成本之和。**陷阱**：忽略资金成本（占用资金的时间价值，资金有成本）和风险溢价（腿风险实际发生概率 × 损失）会高估盈利。跨所搬币有链上确认时间（几小时），期间价差可能消失，转账费 + 时间风险。要算"年化"（小利润高频 vs 大利润低频）。

### Q96. 做市商做市和搬砖套利能共用一套系统吗？

**解析：** 共用：对冲引擎、行情消费、下单通道、风控（底层共享）。不共用：策略决策层（做市双边挂单赚价差 vs 套利跨所对冲赚价差，动机和逻辑不同）。**陷阱**：底层共享，策略层分离；做市账户和套利账户要隔离（风控规则不同——做市限频放宽，套利正常；费率不同——做市 maker rebate，套利正常费率；资金隔离防互相影响）。共用系统降低开发成本 + 统一运维，但要权限分离（做市和套利策略独立配置 + 独立监控）。

## 十六、一致性/分布式事务

### Q97. outbox 模式的"最终一致"和强一致的区别？什么场景必须强一致？

**解析：** outbox 最终一致：DB 事务 + 异步消息，跨系统延迟一致（秒级，消息可能重复但消费幂等保证效果一致）。强一致：跨系统同步事务（2PC/XA），实时一致但性能差（锁定资源 + 协调开销）。交易所：资金 + 委托要强一致（一个 DB 事务，outbox 表同库，冻结 + 委托 + outbox 原子）；成交→行情可最终一致（秒级延迟可接受）。**陷阱**：跨 DB 强一致用 XA 性能差（锁 + 协调），尽量单库事务 + outbox。必须跨系统的强一致（如跨服务资金划转）用 TCC（业务层补偿）。

### Q98. TCC 和 outbox 各适合什么？交易所资金用哪个？

**解析：** TCC：Try-Confirm-Cancel，业务层补偿，适合跨服务长事务（如订单→库存→支付多服务）；实现复杂（每服务三接口）。outbox：DB 事务 + 消息，适合"DB + 消息"场景，简单可靠。交易所资金：单库事务（冻结 + 委托 + outbox 同库），不用 TCC；跨服务（如清算服务 + 资金服务）才 TCC。**陷阱**：TCC 要每个服务实现 Try/Confirm/Cancel 三接口，开发重 + 容易写错（Cancel 要幂等 + 能补偿 Try 的所有副作用）。TCC 的 Confirm/Cancel 可能延迟（要重试框架）。简单场景别上 TCC（过度设计）。

### Q99. 消息重复消费的根因和幂等设计？

**解析：** 根因：Kafka at-least-once（rebalance/ack 丢失导致重消费）+ producer 重试（网络超时但实际发送成功，重发）。幂等：业务唯一键（TradeID/订单ID）+ DB 唯一索引（INSERT 冲突跳过）/ Redis SETNX（标记已处理）。设计：消费前检查"已处理"标记；处理 + 标记同事务（否则处理了没标记=重复处理）。**陷阱**：幂等键要稳定全局唯一且贯穿全链路（不能一段用 A 键一段用 B 键）；不能用消息 offset（不跨 rebalance 稳定，且业务无关）。幂等处理要考虑"部分成功"（处理到一半崩溃，重消费时识别已做部分跳过）。

### Q100. 分布式顺序保证：同一订单的成交顺序怎么跨服务保序？

**解析：** 同 symbol/订单的事件按 key 路由同一 Kafka 分区→单消费者串行→分区顺序。跨服务（撮合→清算→推送）：各段串行 + seq 单调，段间靠 seq 衔接（撮合发 raw_seq，推送层用 push_seq，前端按 push_seq 排序）。**陷阱**：多消费者实例时同 key 必须固定路由（HashPartitioner 按 symbol 固定分区）+ 不跨分区（否则乱序）。消费者并行处理多分区时，分区间无序（但分区内有序），跨 symbol 的全局顺序不需要（各 symbol 独立）。重连增量回放靠 seq 校验连续性，gap 时回退全量。跨服务的 seq 衔接要明确（每段自己的 seq + 段间映射，不能假设全链路一个 seq）。
